# Recovery Grant Claim Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Uniemożliwić równoległym żądaniom użycie tego samego linku odzyskiwania hasła do więcej niż jednej próby `auth.updateUser`.

**Architecture:** Istniejący prywatny grant recovery zostanie rozszerzony addytywnym znacznikiem `claimed_at`. Dwa nowe, ograniczone RPC będą atomowo zajmować i zwalniać grant w kontekście `auth.uid()`. Endpoint Express zachowa obecny klient użytkownika Supabase: najpierw zajmie grant, następnie zmieni hasło, zwolni grant przy błędzie zmiany, a po sukcesie zużyje grant i unieważni sesje.

**Tech Stack:** Node.js 24, natywny `node:test`, Supabase JS 2.110.8, PostgreSQL/Supabase migrations, pgTAP, Prettier, ESLint.

## Task 1: Dodać czerwone testy serwera dla claim/release

**Files:**
- Modify: `test/server.test.js:390-550` — stan syntetycznego grantu, RPC i klient Auth.
- Modify: `test/server.test.js:870-930` — testy sekwencji i błędów endpointu.

**Interfaces:**
- Syntetyczne RPC przyjmą `claim_auth_recovery_grant`,
  `release_auth_recovery_grant` i istniejące `consume_auth_recovery_grant` z
  argumentem `{ grant_jti: "grant-jti-user-a" }`.
- Stan testowy powinien rejestrować `claim`, `release`, `consume` oraz liczbę
  wywołań `auth.updateUser`.

- [ ] **Step 1: Rozszerz fixture o jawny stan grantu**

  W pobliżu `recoveryGrantRpcs` dodaj stan używany wyłącznie przez testy:

  ```js
  const recoveryGrantState = {
    claimed: false,
    claimResult: true,
    releaseResult: true,
    consumeResult: true,
    updateUserCalls: 0,
    updateUserError: null,
  };
  const recoveryGrantEvents = [];
  ```

  W syntetycznym `rpc` zapisuj każde wywołanie do istniejącej tablicy. `claim`
  ma ustawić `claimed = true` tylko wtedy, gdy `claimResult === true` i grant
  nie jest już zajęty; `release` ma wyzerować `claimed`; `consume` ma zwrócić
  `consumeResult`.

- [ ] **Step 2: Dodaj test poprawnej kolejności**

  Rejestruj `updateUser` w `recoveryGrantEvents` obok wywołań RPC. Zmień
  istniejący test zmiany hasła tak, aby przed asercją consume sprawdzał:

  ```js
  assert.deepEqual(recoveryGrantEvents.slice(-3).map(({ name }) => name), [
    "claim_auth_recovery_grant",
    "updateUser",
    "consume_auth_recovery_grant",
  ]);
  assert.equal(recoveryGrantState.updateUserCalls, 1);
  ```

  W praktycznym teście claim będzie zapisany przed `updateUser`; asercje mają
  zostać wykonane na uporządkowanym logu zdarzeń, nie tylko na osobnych
  licznikach.

- [ ] **Step 3: Dodaj test odrzucenia zajętego grantu**

  Ustaw `recoveryGrantState.claimed = true`, wykonaj żądanie do
  `/api/auth/password`, oczekuj statusu `400`, oczekuj braku nowego
  `updateUserCalls` i braku `consume_auth_recovery_grant`.

- [ ] **Step 4: Dodaj test zwolnienia po błędzie `updateUser`**

  Ustaw `updateUserError` na błąd syntetycznego klienta, wykonaj żądanie,
  oczekuj statusu `400`, a następnie sprawdź, że log zawiera
  `claim_auth_recovery_grant`, `release_auth_recovery_grant` i nie zawiera
  consume.

- [ ] **Step 5: Dodaj test braku release po udanej zmianie i błędzie consume**

  Ustaw `consumeResult = false`, wykonaj żądanie, oczekuj statusu `503` oraz
  sprawdź, że grant pozostał zajęty. To utrwala zasadę, że po zmianie hasła
  nie wolno zwalniać grantu i umożliwiać ponownej próby.

- [ ] **Step 6: Uruchom testy i potwierdź czerwony stan**

  Uruchom:

  ```text
  node --test test/server.test.js
  ```

  Oczekiwany wynik: nowe asercje nie przechodzą, ponieważ `server.js` nie
  wywołuje jeszcze claim/release. Nie zmieniaj produkcji przed uzyskaniem tego

## Task 3: Utworzyć addytywną migrację i przejść testy bazy

**Files:**
- Create: timestamped file produced by `supabase migration new add_recovery_grant_claim`.
- Modify: `supabase/tests/database/auth_recovery_grants.test.sql` only if the
  failing contract exposes a missing assertion, not to mask a failure.

**Interfaces:**
- `public.claim_auth_recovery_grant(text) returns boolean`.
- `public.release_auth_recovery_grant(text) returns boolean`.
- `public.consume_auth_recovery_grant(text) returns boolean` remains the
  existing public interface, but requires `claimed_at is not null`.

- [ ] **Step 1: Utwórz plik migracji przez CLI**

  Uruchom:

  ```text
  supabase migration new add_recovery_grant_claim
  ```

  Zapisz SQL w dokładnie wygenerowanym pliku. Nie twórz migracji przez
  ręczne kopiowanie historycznego pliku.

- [ ] **Step 2: Dodaj kolumnę i funkcję claim**

  W migracji użyj idempotentnego:

  ```sql
  alter table private.auth_recovery_grants
    add column if not exists claimed_at timestamptz;
  ```

  `claim_auth_recovery_grant(text)` ma używać `security definer set
  search_path = ''` i jednego `update` z warunkami właściciela z
  `(select auth.uid())`, hasha JTI, `used_at is null`, `expires_at > now()` i
  `claimed_at is null`. Zwróć `row_count = 1`.

- [ ] **Step 3: Dodaj funkcję release i zaostrz consume**

  `release_auth_recovery_grant(text)` ma zerować `claimed_at` tylko dla
  właściciela, pasującego hasha, `used_at is null` i `claimed_at is not null`.
  W `consume_auth_recovery_grant` dodaj warunek `claimed_at is not null`.
  Wszystkie funkcje muszą używać kwalifikowanych nazw `pg_catalog`/
  `extensions`, tak jak istniejący kontrakt.

- [ ] **Step 4: Ustaw dokładne uprawnienia**

  Dla obu nowych funkcji zastosuj:

  ```sql
  revoke all on function public.claim_auth_recovery_grant(text) from public, anon, authenticated;
  revoke all on function public.release_auth_recovery_grant(text) from public, anon, authenticated;
  grant execute on function public.claim_auth_recovery_grant(text) to authenticated;
  grant execute on function public.release_auth_recovery_grant(text) to authenticated;
  ```

  Dla zmienionego consume zachowaj istniejące `revoke` i `grant`, aby nie
  rozszerzać roli klienta.

- [ ] **Step 5: Uruchom testy SQL**

  Uruchom `npm run test:db` i oczekuj przejścia kontraktu recovery oraz
  pozostałych testów bazy. Jeśli testy ujawnią błąd w istniejącej migracji,
  nie poprawiaj go przez zmianę historycznego pliku; zatrzymaj się i zgłoś
  rozbieżność.

## Task 4: Wprowadzić minimalną zmianę endpointu test-first

**Files:**
- Modify: `server.js:1313-1348` — kolejność RPC i kompensacja po błędzie.
- Modify: `test/server.test.js` — dopasowanie syntetycznego klienta do
  dokładnych wywołań produkcji, jeśli Task 1 tego nie obejmuje.

**Interfaces:**
- Endpoint wywołuje `client.rpc("claim_auth_recovery_grant", { grant_jti: grantJti })`.
- Po błędzie `updateUser` wywołuje
  `client.rpc("release_auth_recovery_grant", { grant_jti: grantJti })`.
- Po sukcesie `updateUser` zachowuje istniejące
  `client.rpc("consume_auth_recovery_grant", { grant_jti: grantJti })`.

- [ ] **Step 1: Zaimplementuj claim przed `updateUser`**

  Po udanym `setSession` wywołaj claim. Przy błędzie RPC lub `data !== true`
  zwróć istniejący bezpieczny błąd dla nieważnego/zajętego linku i nie
  wywołuj `updateUser`.

- [ ] **Step 2: Zaimplementuj release wyłącznie przy błędzie zmiany hasła**

  Po `updateUser` z błędem wykonaj próbę release w bezpiecznym bloku. Błąd
  release nie może zastąpić komunikatu dla użytkownika ani ujawnić szczegółów
  RPC. Następnie zwróć obecny status 400 dotyczący nieudanej zmiany hasła.

- [ ] **Step 3: Zachowaj grant po błędzie consume**

  Nie wywołuj release po udanym `updateUser`. Przy błędzie lub `false` z
  consume zachowaj status 503 i zaloguj wyłącznie ogólny komunikat bez JTI,
  tokenów, haseł i ciasteczek.

- [ ] **Step 4: Uruchom testy serwera**

  Uruchom:

  ```text
  node --test test/server.test.js
  npm run check
  ```

  Oczekuj przejścia testów sekwencji, zajętego grantu, release po błędzie
  `updateUser`, błędu consume i istniejących testów auth/legal.
